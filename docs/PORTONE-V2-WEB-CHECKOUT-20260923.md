# Blade Surge web/PWA PortOne V2 verification contract

This is a source check for the next disabled order-ledger candidate. It is specific to Blade Surge web/PWA. It does not bind TLLHOUSE or another product's KG Inicis account, MID, store, channel or approval, and it is not a checkout implementation.

## Official surface checked on 2026-09-23

The PortOne documentation index MCP returned an empty listing, but its V2 OpenAPI summary and targeted schema reads worked. The schema reports OpenAPI 3.0.3, PortOne API 1.16.0, `https://api.portone.io`, and the `portOne` authorization scheme (`Authorization: PortOne <API secret>`). The official Inicis card examples were read for React and Express; their sample IDs are examples, not this product's credentials. References: [PortOne V2 REST API](https://developers.portone.io/api/rest-v2?v=v2) and [Inicis integration](https://developers.portone.io/opi/ko/integration/inicis?v=v2). Exact schema selectors used: `paths./payments/{paymentId}.get`, `paths./payments/{paymentId}/cancel.post`, `components.schemas.Payment`, `PaidPayment`, `PartialCancelledPayment`, `PaymentAmount`, `SelectedChannel`, `PaymentCancellation`, `SucceededPaymentCancellation`, `CancelPaymentBody`, `PgProvider` and `components.securitySchemes`.

| Provider fact | Server rule before a grant or reversal |
|---|---|
| `GET /payments/{paymentId}` returns a `Payment` union. `status` includes `READY`, `PAY_PENDING`, `VIRTUAL_ACCOUNT_ISSUED`, `PAID`, `PARTIAL_CANCELLED`, `CANCELLED`, `FAILED`. | A browser return or webhook only queues reconciliation. Fetch the actual payment with a server secret. Grant only after a verified `PAID` record matches a previously persisted order; hold all other states for explicit reconciliation. |
| A paid record requires `id`, `merchantId`, `storeId`, `channel`, `version`, `orderName`, `amount`, `currency`, `paidAt`. `channel` requires `type`, `pgProvider`, `pgMerchantId`; `id` and `key` may be present. | Compare payment ID, V2, the **Blade-approved** store/merchant/channel binding, frozen order name, KRW and frozen catalog amount. Channel `TEST` and `LIVE` are separate evidence. Do not infer the active Inicis enum or channel ID from an example: the schema contains `INICIS`, `HTML5_INICIS`, `INICIS_UNIFIED` and `INICIS_V2`. |
| `PaymentAmount` distinguishes `total`, `paid`, `discount` and `cancelled`. `customData` is an optional string. | Define the approved discount/promotion rule before allowing one; compare the provider's actual paid amount and accepted discount against the frozen order. Never derive the SKU, player or grant solely from `customData`, the redirect or a client amount. |
| A cancellation can be `REQUESTED`, `FAILED` or `SUCCEEDED`. Paid, partially cancelled and cancelled payment variants may carry cancellation entries; successful entries have an `id` and `totalAmount`. | Apply an idempotent reversal only for a final `SUCCEEDED` cancellation ID; reconcile partial versus full cancellation against the provider's `amount.cancelled`. Keep pending/failed cancellation from silently changing entitlement. |
| `POST /payments/{paymentId}/cancel` requires `reason`; `amount` omitted means full cancellation and `currentCancellableAmount` is an optional balance check. | A future product-specific refund path must calculate the amount and current cancellable balance from its server ledger and provider state, then reconcile the resulting payment. This document does not call the API or authorize a refund. |

The official backend example and [V2 webhook guide](https://developers.portone.io/opi/ko/integration/webhook/readme-v2?v=v2) verify webhook signatures over the raw request body with a dedicated webhook secret, then call `getPayment` again. A future Worker implementation needs a compatible, tested raw-body signature path and independent provider read; a parsed or unsigned event is never grant proof. The example's client-generated payment ID must be replaced by a server-persisted order/payment ID before opening checkout. Store IDs, channel keys, API/webhook secrets, approved merchant/PG mapping and sandbox responses must be read from Blade's own authorized account route, never copied from examples or another product.

## Next implementation gate

Keep the 13-item catalog disabled and `/api/commerce/orders` at 503. Next build a server-owned order/entitlement schema behind a disabled route, with one authenticated subject, immutable SKU/version/amount/channel snapshot, idempotency and payment ID uniqueness. Test duplicate requests, mismatched provider records, late or repeated paid events, partial/full cancellation and already-spent goods against local D1 before opening a sandbox checkout. Cloudflare Worker compatibility of the PortOne server SDK or direct REST client, webhook verifier, rate limits, approved Blade TEST channel, merchant data and actual provider responses are still unverified. Play, ONE Store and Apps in Toss use separate billing proof.
