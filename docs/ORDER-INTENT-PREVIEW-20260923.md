# Blade Surge immutable order-intent preview

This candidate adds a local D1 table for an order **preparation record**, not a checkout or entitlement. It is stacked on the disabled commerce backend and PortOne V2 source contract. The production Worker still has no `COMMERCE_DB` binding, and `/api/commerce/orders` still returns `503 billing-unavailable` before any database access.

`migrations/0002_commerce_order_intents_preview.sql` permits only `PREPARED` rows. Each row freezes one non-null order ID, player, WEB channel, idempotency key, catalog version/SKU, integer KRW amount, provider payment ID, and store/channel identifiers. A matching catalog version, SKU, price and currency are required by trigger. `(player_id, sales_channel, idempotency_key)` and `payment_id` are unique; updates and deletes are rejected. An insert trigger rejects existing order, payment and retry identities before SQLite `INSERT OR REPLACE` can discard the original row. The table contains no paid state, grant, wallet, refund, credential or webhook event. These constraints are groundwork for a future authenticated server adapter; they do not themselves authenticate the player or prove provider payment. A future adapter must read the existing row on a retry and reject conflicting retry details rather than assume `INSERT OR IGNORE` means compatibility. Retention and deletion require a later explicit, reviewed policy.

`migrations/0003_commerce_merchant_snapshot_preview.sql` adds a merchant ID snapshot without rewriting existing 0002 data. New PREPARED inserts must carry a nonblank value; existing rows remain `NULL` because the actual Blade-approved merchant cannot be inferred. The immutable-row trigger prevents an ad hoc backfill. Any future paid verifier must reject a legacy `NULL` merchant row and compare a new row's stored merchant ID to PortOne `PaidPayment.merchantId` and the approved Blade account binding. Neither a client field nor a documentation example is authority. The local fixture strings do not prove Blade's real merchant identity.

Verified locally on 2026-09-23: four focused Bun SQLite invariant tests pass; final full `bun run check` passed with 970 tests, one pre-existing exploratory skip, typecheck and Vite build. Fresh Wrangler 4.128.0 local D1 databases applied migrations 0001 and 0002. One accepted a `PREPARED` fixture row and rejected duplicate player/channel/idempotency key, `PAID` mutation, `INSERT OR REPLACE` of the original row, and deletion; the original remained at `starter`/1,200 KRW/`PREPARED`. A second fresh D1 rejected a `NULL` order ID with `SQLITE_CONSTRAINT_NOTNULL`. No remote D1 or provider call was made. The fixture store/channel strings are local test literals, not approved Blade account values.

2026-09-24 additive-migration verification: a new Bun SQLite regression creates a 0002 legacy row, applies 0003, verifies that row remains `NULL`/immutable, rejects an insert without merchant ID, and accepts a new merchant-bound row. Fresh local Wrangler D1 applied 0001, 0002 and 0003 via SQL files, accepted one `PREPARED` row with a merchant ID, rejected an empty merchant with `SQLITE_CONSTRAINT_TRIGGER`, and retained only the valid row. This is local schema proof, not approved account mapping or live payment proof.

Before any checkout route opens, the product still needs a recoverable activated identity, approved Blade TEST and LIVE store/channel mapping, server-owned catalog grant definition, provider verification and idempotent paid/partial-refund/reversal ledger, plus same-candidate sandbox and device checks. This table cannot be promoted into those states by changing a flag; a separate reviewed migration and application path are required. Play, ONE Store and Apps in Toss billing remain separate.
