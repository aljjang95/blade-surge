# Blade Surge disabled commerce backend candidate

Base: draft PR #68 head `be34c78d55bb44ebed63b1cc33b39ff0df51bc0a`. This candidate does not make any product purchasable.

`worker/commerce.ts` exposes a server catalog only when a D1 binding exists and the seeded version matches all 12 mock cash SKUs plus the pass at their recorded KRW amounts. Every row is constrained to `sale_enabled = 0`. A partial, changed or enabled catalog fails closed. `/api/commerce/orders` always returns `503 billing-unavailable`. The production `wrangler.jsonc` has no commerce D1 binding, identity flag, Google client ID or HMAC secret, so neither the catalog nor player lookup activates on deploy.

`GET /api/commerce/me` is also disabled by default. If explicitly configured later, it accepts a Google ID token only after checking its RS256 signature with Google's fixed public-key endpoint, exact configured client audience, allowed issuer and unexpired claim. The public keys are cached per Worker isolate for a bounded Cache-Control lifetime; failed fetches are briefly cached too, so malformed or forged tokens do not trigger one upstream fetch each. Google's two documented issuer spellings normalize to one subject. The provider subject is HMAC-derived before storage in `commerce_subjects`; the raw token, email and provider subject are not stored in D1 or returned. Each HMAC key is bound to one version by a fixed-message proof in `commerce_key_versions`, without storing the key. During rotation, the prior key and version must remain configured until every prior player has a new-version mapping; a wrong prior key, same-version key replacement, or early retirement fails closed. Older mapped versions do not block a subsequent rotation, while an older unmapped account does. This is an identity foundation, not a finished login session or account recovery/deletion flow. The frontend does not request Google sign-in and no account creation is enabled in the shipped config.

Local proof: Bun `1.4.2` frozen install, focused commerce tests, full `bun run check`, Wrangler `4.128.0` production-config dry-run, and actual local workerd/D1 preview are required for this PR. The local D1 seed must show 13 distinct rows and zero enabled rows; local HTTP must show catalog `200` with 13 disabled items, order `503`, and identity `503`. Rotation tests must reject a changed key under the same version, a wrong previous key, and early previous-key retirement while preserving the existing player ID with the correct pair. Local configuration and DB bytes remain under ignored `work/`. The installed workerd supports compatibility date through `2026-09-07`, so the ignored local test config uses that date; the production config and lockfile are unchanged.

Before a sale, connect an approved login UX, stable recovery and deletion, protected identity activation, production D1 binding and secret lifecycle, server-owned grants/spends/claims and provider-verified orders/refunds. Keep the cash-grant guard in draft PR #67 separate. Play, ONE Store and Apps in Toss require their own billing and receipt evidence.

The preview rotation check does not coordinate old and new deployed writers. A future activation or key rotation requires a controlled single-writer cutover, a production subject-mapping audit, request-rate controls, and a tested rollback before the prior key can be retired. Neither the local fixture nor this PR authorizes that rollout.

Verified locally on 2026-09-23: frozen Bun `1.4.2` lockfile; focused commerce tests 9/9; final full typecheck, 966 passing tests with one pre-existing exploratory skip, and Vite build; Wrangler `4.128.0` production-config dry-run without a commerce D1 binding. Fresh local D1 migration executed five statements; 13 distinct catalog rows and zero enabled rows. Local workerd returned catalog 200 with 13 disabled items, orders 503 and identity 503. Local D1 rotation SQL reported one unmigrated prior account before new-version mapping and zero after, while same-version proof replacement and proof reuse were rejected. A follow-up D1 query for a second rotation returned only the immediately prior version as pending. Tests also cover a second rotation, an older orphan and public-key fetch reuse. These checks do not prove live Google sign-in, remote D1, payment, entitlement, device or store behavior.
